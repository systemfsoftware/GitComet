### 8. [HIGH] Unbounded memory read of hostile `git diff` output via Diff::from_unified_reader
- **Where**: `crates/gitcomet-core/src/domain.rs:892` (deep:parsers, confidence high)
- **What**: Diff::from_unified_reader reads the entire child stdout into a String via `reader.read_to_string(&mut text)?` with NO size cap. The reader is the stdout pipe of `git diff` (or `git show --no-ext-diff --pretty=format: <commit>`), and the diff output reflects the contents of arbitrary blobs in the opened repository. An attacker who controls the repository contents can stage a commit whose single-blob diff produces arbitrarily large output (no upper bound on `git diff` stdout for a blob that is gigabytes long). Although the child process is bounded by `git_command_timeout()` (kill after a default window), `read_to_string` is racing the timeout: by the time the kill lands, the pipe buffer plus the String allocation can consume hundreds of MB to several GB of RAM before the kernel kills the child and the read returns. There is also no check on the resulting `Vec<DiffLine>` after parsing — a 10 GB unified diff produces a 10 GB String, then is split into lines. The only subsequent bound is `Vec::with_capacity(line_capacity_from_bytes)` which is `newline_count + 1` — still bounded by the now-oversized String. Net effect: opening a hostile repo and viewing a file diff (commit, working tree, or range) is sufficient to OOM the process via a single user action; no special tooling needed.
- **Dataflow**: 1. User opens hostile repo and clicks a commit/file in the history pane. 2. UI calls GitRepository::diff_parsed_impl / diff_parsed_cancellable_impl / diff_unified_impl (crates/gitcomet-git-gix/src/repo/diff.rs:95-157). 3. build_unified_diff_command spawns `git diff` (or `git show`) with stdin/stdout piped, no --patch-with-stat limit (diff.rs:33-93). 4. run_git_parsed_stdout_maybe_cancellable spawns the child and hands the pipe to a parser thread (util.rs:720-799). 5. The parser is `Diff::from_unified_reader(target, BufReader::new(stdout))` (domain.rs:892-899). 6. `reader.read_to_string(&mut text)` consumes the pipe until EOF, allocating a String sized to the full diff output (no `.take()` cap, no `max_len` argument). 7. `Diff::from_unified_owned` builds a `Vec<DiffLine>` by memchr-scanning the now-oversized String (domain.rs:856-879). Process RSS equals the String size + per-line SharedLineText wrappers + the in-flight pipe buffer; for a multi-GB output this OOMs before the timeout's kill propagates.
- **Exploit**: 1. As attacker, commit a single large file (e.g. `dd if=/dev/zero of=huge.bin bs=1M count=2048 && git add huge.bin && git commit -m x`). 2. User opens the repo in GitComet and views any commit, or any file diff against that commit. 3. `git diff <commit>` produces ~2 GB of stdout (the blob's full contents on the `+` side). 4. Diff::from_unified_reader materializes a 2 GB String and a multi-million-element Vec<DiffLine>, OOMing the GitComet process. No user interaction beyond opening the repo + clicking the commit is required.
- **Fix**: Wrap the read with a `std::io::Read::take(max_bytes)` cap in `Diff::from_unified_reader` (and the underlying pipe in run_git_parsed_stdout_maybe_cancellable). Pick a per-diff ceiling on the order of 16-64 MiB; this is the size budget that the UI can actually render, and any output above it is a parser DoS regardless of intent. Pair with a per-line budget (`max_lines`) so a hostile output that contains only short lines cannot evade the byte cap.
